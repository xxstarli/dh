# 个人导航网站 V1｜数据结构与业务规则

> 文档版本：V1.0  
> 对应文档：`01_PRD.md`、`02_UI与交互说明.md`  
> 使用对象：Codex / 后端开发 / 全栈开发  
> 本文档用于定义 V1 的数据模型、字段约束、业务规则、排序逻辑、鉴权规则及接口行为。  
> 如本文档与 PRD 冲突，以 PRD 为最高优先级。

---

# 1. 设计原则

V1 数据层遵循以下原则：

1. 结构简单。
2. 数据可持久化。
3. 不为未来可能需求提前复杂化。
4. 不设计多用户体系。
5. 不设计复杂权限表。
6. 不设计二级分类。
7. 不设计标签、收藏、访问统计等额外表。
8. 排序规则明确且可持久化。
9. 所有写操作必须经过管理权限校验。
10. 数据库结构需支持后续平滑扩展，但 V1 不提前实现未定义功能。

---

# 2. 核心数据对象

V1 建议仅保留以下核心对象：

```text
Category
Site
Settings
AdminSession / 管理会话
```

其中：

- `Category`：网站分类。
- `Site`：具体网站卡片。
- `Settings`：站点级基础配置。
- `AdminSession`：用于管理模式鉴权，不一定必须持久化为数据库表，可采用安全 Cookie / Session 方案实现。

---

# 3. Category｜分类表

建议表名：

```text
categories
```

推荐字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| id | UUID / CUID / String | 是 | 主键 |
| name | String | 是 | 分类名称 |
| sort_order | Integer | 是 | 分类排序 |
| created_at | DateTime | 是 | 创建时间 |
| updated_at | DateTime | 是 | 更新时间 |

---

## 3.1 id

要求：

- 系统自动生成。
- 全局唯一。
- 前端不可自行生成业务含义型 ID。
- 推荐使用 UUID、CUID 或数据库原生唯一 ID。

---

## 3.2 name

分类名称。

规则：

- 必填。
- 去除首尾空格。
- 不允许纯空格。
- 建议最大长度：30 个字符。
- V1 不强制分类名称唯一。

例如：

```text
常用
AI 工具
开发工具
办公工具
卡牌业务
```

### 是否允许重名

V1：

> 允许分类重名。

原因：

自用场景数据量小，不需要增加复杂唯一约束。

但 UI 上不建议主动创建重名分类。

---

## 3.3 sort_order

用于控制分类首页顺序。

规则：

- 必填。
- 整数。
- 数值越小越靠前。
- 新建分类默认排在最后。
- 拖拽排序后更新。

建议从：

```text
1000
2000
3000
```

或：

```text
1
2
3
```

开始。

实现方式可由开发决定。

V1 不要求必须连续。

---

# 4. Site｜网站表

建议表名：

```text
sites
```

推荐字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| id | UUID / CUID / String | 是 | 主键 |
| category_id | String | 是 | 所属分类 |
| name | String | 是 | 网站名称 |
| url | String | 是 | 网站地址 |
| icon_type | Enum / String | 是 | 图标来源 |
| icon_url | String / Nullable | 否 | 图标地址 |
| description | String / Nullable | 否 | 网站说明 |
| sort_order | Integer | 是 | 当前分类内排序 |
| created_at | DateTime | 是 | 创建时间 |
| updated_at | DateTime | 是 | 更新时间 |

---

# 5. Site.category_id

所属分类 ID。

规则：

- 必填。
- 必须引用现有分类。
- 一个网站只能属于一个分类。
- 一个分类可以包含多个网站。

关系：

```text
Category 1 ───── N Site
```

建议数据库建立外键。

删除分类时：

> 不允许数据库自动级联删除网站。

推荐：

```text
ON DELETE RESTRICT
```

或在业务层阻止删除非空分类。

---

# 6. Site.name

网站名称。

规则：

- 必填。
- 去除首尾空格。
- 不允许纯空格。
- 建议最大长度 30 字符。
- 不要求唯一。

例如：

```text
ChatGPT
GitHub
Vercel
```

允许：

> 同名网站存在于不同分类。

---

# 7. Site.url

网站访问地址。

规则：

- 必填。
- 保存前去除首尾空格。
- 必须为合法 HTTP / HTTPS URL。
- V1 仅允许：

```text
http://
https://
```

不接受：

```text
javascript:
data:
file:
ftp:
```

等协议。

---

## 7.1 自动补全协议

用户输入：

```text
example.com
```

系统自动标准化为：

```text
https://example.com
```

用户输入：

```text
www.example.com
```

转换为：

```text
https://www.example.com
```

已有：

```text
http://
https://
```

时不重复添加。

---

## 7.2 URL 重复规则

V1：

> 不限制 URL 唯一。

允许：

```text
GitHub
```

同时存在于：

```text
常用
开发工具
```

因此：

> `url` 不建立唯一索引。

---

## 7.3 URL 安全规则

保存前应：

- 校验协议。
- 禁止脚本协议。
- 输出到前端时做安全处理。
- 打开网站使用安全的新标签方式。

建议：

```text
target="_blank"
rel="noopener noreferrer"
```

---

# 8. Site.description

网站说明。

规则：

- 选填。
- 允许空值。
- 去除首尾空格。
- 建议最大长度 50 字符。
- 卡片中仅显示一行。

例如：

```text
AI 对话助手
代码托管与协作
网站部署平台
```

如果为空：

> 前端显示网站域名。

数据库中无需自动写入域名。

---

# 9. 网站图标数据结构

V1 推荐区分图标来源。

字段：

```text
icon_type
icon_url
```

推荐 `icon_type` 值：

```text
auto
custom
default
```

---

## 9.1 auto

表示使用系统自动获取的网站 Favicon。

例如：

```text
icon_type = "auto"
icon_url = "https://..."
```

如果实际实现采用内部代理接口或缓存地址，也可以保存系统生成的图标地址。

---

## 9.2 custom

表示用户手动上传图标。

例如：

```text
icon_type = "custom"
icon_url = "/uploads/sites/xxx.webp"
```

优先级最高。

---

## 9.3 default

自动获取失败且用户未上传时使用。

可以：

```text
icon_type = "default"
icon_url = null
```

前端直接显示系统内置默认图标。

---

## 9.4 图标优先级

显示逻辑必须遵循：

```text
custom
  ↓
auto
  ↓
default
```

---

# 10. 图标获取规则

用户填写网站地址后，可触发自动获取 Favicon。

业务要求：

1. 图标获取属于辅助功能。
2. 获取失败不得阻止网站保存。
3. 自动获取应有超时机制。
4. 不得因为目标网站异常导致添加网站流程长时间卡住。
5. 获取失败时直接使用默认图标。

---

## 10.1 获取时机

推荐：

> URL 输入框失焦后或 URL 校验通过后触发。

也可以：

> 点击“重新获取”手动触发。

无需每次输入一个字符都发请求。

---

## 10.2 编辑 URL 后

如果网站地址发生变化：

建议：

- 当前 `icon_type = auto` 时，可重新获取新图标。
- 当前 `icon_type = custom` 时，不自动覆盖用户上传图标。

---

## 10.3 恢复自动获取

如果当前为自定义图标，用户点击：

> 恢复自动获取

则：

```text
icon_type = auto
```

并尝试重新获取当前 URL 的 Favicon。

---

# 11. 上传图标规则

允许格式：

```text
PNG
JPG
JPEG
WebP
```

建议大小：

```text
≤ 2MB
```

要求：

- 服务端校验 MIME Type。
- 服务端校验文件大小。
- 不仅依赖前端文件扩展名。
- 上传后生成安全文件名。
- 禁止使用用户原始文件名直接作为服务器路径。
- 如部署平台支持对象存储，可保存对象存储 URL。

V1 不要求：

- 图片裁剪
- 图片编辑
- 多尺寸版本管理

---

# 12. Site.sort_order

控制网站在当前分类中的顺序。

规则：

- 必填。
- 仅在 `category_id` 范围内生效。
- 数值越小越靠前。
- 新增网站默认排在所属分类最后。

---

# 13. Settings｜站点设置

建议表名：

```text
settings
```

V1 可以采用单行配置。

推荐字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| id | String | 是 | 固定单条配置 |
| site_name | String | 是 | 网站名称 |
| site_logo | String / Nullable | 否 | Logo |
| admin_password_hash | String | 是 | 管理密码哈希 |
| created_at | DateTime | 是 | 创建时间 |
| updated_at | DateTime | 是 | 更新时间 |

---

# 14. site_name

默认：

```text
我的导航
```

V1 可以通过：

- Seed
- 环境变量
- 数据库初始化

写入。

由于 V1 暂不设计独立设置页面：

> 不要求提供在线修改入口。

---

# 15. site_logo

选填。

如果为空：

> 前端显示系统默认 Logo。

V1 不要求在线上传站点 Logo。

如果后续需要可再扩展。

---

# 16. admin_password_hash

管理密码禁止明文存储。

必须保存：

> 密码哈希。

推荐：

- Argon2
- bcrypt

不得：

- 明文
- Base64
- 可逆加密当作密码存储

---

# 17. 管理鉴权模型

V1 不设计用户表。

推荐：

```text
一个管理密码
        ↓
服务端验证
        ↓
创建管理 Session
        ↓
浏览器保存 HttpOnly Cookie
```

---

# 18. 管理 Session

推荐属性：

```text
HttpOnly
Secure（HTTPS 环境）
SameSite=Lax 或 Strict
```

管理 Session 应：

- 服务端生成
- 不把管理密码存入 Cookie
- 不把明文密码回传给客户端

---

## 18.1 有效期

自用场景建议：

```text
Session Cookie
```

关闭浏览器后失效。

或者设定一个较短有效期，例如：

```text
12 小时
24 小时
```

开发可根据实现选择。

V1 不需要：

- Remember Me
- 多设备管理
- Session 管理后台

---

# 19. 普通访问权限

无需登录即可：

- 获取分类
- 获取网站
- 搜索网站（前端完成即可）
- 打开网站

---

# 20. 管理访问权限

以下操作必须在服务端校验管理 Session：

- 新增分类
- 编辑分类
- 删除分类
- 分类排序
- 新增网站
- 编辑网站
- 删除网站
- 网站排序
- 图标上传

前端隐藏按钮：

> 不能代替服务端权限校验。

---

# 21. 分类新增规则

输入：

```text
name
```

处理流程：

```text
接收分类名称
  ↓
trim
  ↓
校验非空 / 长度
  ↓
计算当前最大 sort_order
  ↓
追加到最后
  ↓
保存
```

---

# 22. 分类编辑规则

允许修改：

```text
name
```

不允许通过普通编辑接口修改：

```text
id
created_at
```

排序必须通过排序接口处理。

---

# 23. 分类删除规则

删除前必须查询：

```text
该分类下网站数量
```

如果：

```text
count > 0
```

拒绝删除。

返回明确业务错误：

```text
当前分类下还有 X 个网站，请先移动或删除这些网站。
```

如果：

```text
count = 0
```

允许删除。

---

# 24. 分类排序规则

客户端提交：

```text
category_ids
```

例如：

```json
[
  "cat_3",
  "cat_1",
  "cat_2"
]
```

服务端根据数组顺序更新：

```text
sort_order
```

例如：

```text
cat_3 → 1
cat_1 → 2
cat_2 → 3
```

要求：

- 必须校验所有 ID 合法。
- 不得接受重复 ID。
- 不得包含不存在的分类。
- 建议在事务中完成。
- 更新失败时整体回滚。

---

# 25. 网站新增规则

输入字段：

```text
name
url
description
category_id
icon
```

处理：

```text
验证管理权限
  ↓
验证分类存在
  ↓
校验名称
  ↓
标准化 URL
  ↓
校验 URL
  ↓
处理图标
  ↓
计算该分类最大 sort_order
  ↓
追加到最后
  ↓
保存
```

---

# 26. 网站编辑规则

允许修改：

```text
name
url
description
category_id
icon
```

---

## 26.1 分类未变化

如果：

```text
new_category_id == old_category_id
```

则：

> 保持原 `sort_order`。

---

## 26.2 分类发生变化

如果：

```text
new_category_id != old_category_id
```

则：

1. 验证新分类存在。
2. 设置新 `category_id`。
3. 新 `sort_order` = 新分类最后一个位置。
4. 原分类剩余网站排序保持相对顺序。

无需强制把原分类所有 `sort_order` 连续重排。

---

# 27. 网站删除规则

删除网站后：

- 不需要强制立即重新编号所有 `sort_order`。
- 页面读取时按排序字段正常显示即可。

例如原排序：

```text
1
2
3
4
```

删除 2 后可以保留：

```text
1
3
4
```

后续拖拽排序时重新标准化即可。

这样实现更简单。

---

# 28. 网站排序规则

网站排序接口只允许：

> 同一个分类内排序。

客户端提交：

```text
category_id
site_ids
```

例如：

```json
{
  "category_id": "cat_1",
  "site_ids": [
    "site_4",
    "site_2",
    "site_1",
    "site_3"
  ]
}
```

服务端必须校验：

1. 分类存在。
2. 所有网站都属于该分类。
3. 不存在重复 ID。
4. 不允许包含其他分类的网站。
5. 推荐校验提交集合与当前分类网站集合一致。

通过后：

```text
site_4 → sort_order 1
site_2 → sort_order 2
site_1 → sort_order 3
site_3 → sort_order 4
```

在数据库事务中执行。

---

# 29. 网站跨分类规则

V1：

> 不支持通过拖拽跨分类。

跨分类只能通过：

```text
编辑网站
  ↓
修改所属分类
  ↓
保存
```

保存后：

> 网站自动进入新分类最后。

---

# 30. 搜索业务规则

V1 搜索建议前端完成。

原因：

- 数据量小
- 首页已获取全部分类和网站
- 无需增加搜索 API 复杂度

搜索字段：

```text
site.name
site.description
site.url / hostname
```

建议：

- 不区分大小写。
- trim 搜索关键词。
- 空关键词显示全部。
- 分类名称本身不作为核心搜索字段。

---

# 31. 搜索结果规则

过滤后：

- 分类中至少有 1 个匹配网站 → 显示该分类。
- 分类中 0 个匹配网站 → 隐藏该分类。

搜索不修改数据库。

不修改：

- `sort_order`
- 分类关系

---

# 32. 数据读取规则

首页数据建议一次返回：

```json
{
  "settings": {
    "site_name": "我的导航",
    "site_logo": null
  },
  "categories": [
    {
      "id": "cat_1",
      "name": "常用",
      "sort_order": 1,
      "sites": [
        {
          "id": "site_1",
          "name": "ChatGPT",
          "url": "https://chatgpt.com",
          "icon_type": "auto",
          "icon_url": "...",
          "description": "AI 对话助手",
          "sort_order": 1
        }
      ]
    }
  ]
}
```

排序要求：

```text
categories.sort_order ASC
sites.sort_order ASC
```

---

# 33. 空分类读取

普通模式：

前端可隐藏空分类。

后台接口：

> 建议仍然返回空分类。

原因：

管理模式需要显示空分类。

是否展示由前端根据当前模式决定。

# 34. 推荐 API 设计

具体框架可调整，但语义建议如下。

---

## 34.1 公共接口

### 获取首页数据

```text
GET /api/navigation
```

返回：

- Settings
- Categories
- Sites

无需管理权限。

---

# 35. 管理鉴权接口

### 管理登录

```text
POST /api/admin/login
```

请求：

```json
{
  "password": "..."
}
```

成功：

```json
{
  "success": true
}
```

并设置安全 Session Cookie。

---

### 管理退出

```text
POST /api/admin/logout
```

清除 Session。

---

### 检查管理状态

可选：

```text
GET /api/admin/session
```

返回：

```json
{
  "authenticated": true
}
```

---

# 38. 图标 API

可选设计：

### 自动获取 Favicon

```text
POST /api/admin/favicon
```

请求：

```json
{
  "url": "https://example.com"
}
```

返回：

```json
{
  "success": true,
  "icon_url": "..."
}
```

获取失败：

```json
{
  "success": false,
  "icon_url": null
}
```

注意：

> 图标获取失败不是业务错误，不应返回导致表单无法继续的致命状态。

---

# 39. 上传 API

例如：

```text
POST /api/admin/uploads/site-icon
```

要求：

- 管理权限

# 51. Favicon 获取安全

如果服务端需要请求用户输入的网站地址：

必须防范：

> SSRF

至少应：

- 只允许 HTTP/HTTPS
- 禁止 localhost
- 禁止 127.0.0.1
- 禁止内网私有 IP 段
- 禁止云服务 metadata 地址
- 限制重定向
- 设置请求超时
- 限制返回内容大小

如果采用第三方 favicon 服务：

> 不应把管理密码或敏感数据发送出去。

# 55. 开发实现约束

Codex 开发时必须遵循：

1. 一个网站只能属于一个分类。
2. 分类和网站均采用显式排序字段。
3. URL 不做唯一约束。
4. 分类名称不强制唯一。
5. 非空分类禁止删除。
6. 删除分类不得级联删除网站。
7. 网站拖拽禁止跨分类。
8. 修改分类通过编辑网站完成。
9. 新增网站放分类末尾。
10. 修改分类后放新分类末尾。
11. 所有写接口必须服务端鉴权。
12. 管理密码必须哈希存储。
13. Favicon 获取失败不得阻塞保存。
14. 图标上传必须做类型及大小校验。
15. 页面刷新后所有数据和排序必须保留。
16. 不得以 localStorage 作为最终数据库。
17. 不得仅依赖前端隐藏按钮实现权限控制。
18. 排序批量更新推荐使用事务。
19. 不得为了 V1 增加复杂多用户数据结构。
20. 不得创建 PRD 未定义的业务字段和功能。

# 57. 最终业务模型

V1 的核心关系可以简化为：

```text
Settings
   │
   └── 定义站点基础信息和管理密码

Category
   │
   ├── Site
   ├── Site
   ├── Site
   └── ...

Category
   │
   ├── Site
   └── ...
```

管理规则：

```text
管理密码
   ↓
服务端验证
   ↓
管理 Session
   ↓
允许增 / 删 / 改 / 排序
```

排序规则：

```text
Category.sort_order
Site.category_id + Site.sort_order
```

这就是 V1 完整的数据和业务核心。

不需要再增加额外业务模型。
